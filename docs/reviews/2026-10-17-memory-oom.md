# 2026-10-15 内存耗尽分析

## 结论

已定位一个能解释本次长期堆增长、并可独立复现的泄漏路径：数据库后端 `Backend.guard()` 以传入的 `Context` 对象作为 `WeakMap` 键；Cordis 服务调用会生成不同身份的影子上下文，重复访问数据库时缓存不断失效，反复通过 `ctx.effect()` 注册卸载回调。回调保留上下文、guard 和 Cordis 用于诊断的调用栈，插件持续运行期间不会释放。

本次完成日志分析、快照引用链核对和隔离复现，未修改业务代码，未验证修复后的长期运行。

## 堆快照与引用链

快照大小 3,890,253,124 字节，包含 36,840,404 个节点和 190,480,263 条引用边。按 V8 `self_size` 汇总的部分结果如下；这些是浅层大小，不是可相加到某个根对象上的保留大小。

| 对象类别                               |      数量 | 浅层大小（MiB） |
| -------------------------------------- | --------: | --------------: |
| 对象属性存储数组 `(object properties)` | 7,460,853 |         1716.18 |
| 闭包（全部）                           | 8,581,878 |          458.37 |
| `system / Context`                     | 5,227,713 |          249.06 |
| `system / CallSiteInfo`                | 3,578,331 |          191.10 |
| `Error`                                |   358,189 |           16.39 |

追踪主要 Fiber 的 `_disposables.map`，再从回调沿 `context → runner → execute → shared → script` 分类，发现下列回调指向数据库实现的同一段 guard 注册函数（快照节点索引 96217）：

| 所属生命周期                 | 数据库 guard 回调数量 |
| ---------------------------- | --------------------: |
| IdentityImService            |               102,375 |
| workspace-file 的 IM 集成    |                86,144 |
| ImAiService                  |                77,989 |
| workspace-file 的 Agent 集成 |                62,685 |
| im-onebot                    |                27,148 |
| 合计                         |               356,341 |

代表性强引用链：

```text
ImAiService 所属 Fiber
  → _disposables → map → 卸载回调
  → 闭包 context → runner → execute
  → 闭包 context → previous → { this: Backend, ctx: 影子上下文 }
```

同一个 runner 的 `getOuterStack` 还持有 `outerError`，保留调用栈及其关联对象。这解释了大量 Error 和 CallSiteInfo；它们不代表发生了同等数量的业务异常。

快照内的数据库源码确认使用 `owners = new WeakMap`、`owners.get(ctx)` 和 `ctx.effect(() => () => { active = false; owners.delete(ctx) })`。当前源码对应 `plugins/implementations/database-kysely/src/index.ts` 的 `guard()`，第 27、41–56 行。

虽然缓存是 WeakMap，但其键还被 Fiber 中的卸载回调强引用，因此 WeakMap 不能使这些对象自动回收。IM 的 workers、requests、activeRuns 对应的表在快照中都很小，不是主要积累点。

## 隔离复现

在独立进程中使用当前项目 Cordis、数据库定义插件和真实 SQLite 内存数据库，没有连接业务数据库或调用真实模型。创建一个 Service，其方法重复执行：

```typescript
return this.ctx.database.scope(this.ctx, 'memory-probe')
```

通过依赖注入上下文调用该服务 1000 次，再对照使用固定的所属上下文调用 1000 次，直接统计 Fiber 的卸载回调数量：

| 阶段                             | 服务所属 Fiber | 调用方 Fiber |
| -------------------------------- | -------------: | -----------: |
| 初始                             |              1 |            0 |
| 经服务代理调用 1000 次后         |              1 |         1000 |
| 再用固定所属上下文调用 1000 次后 |              2 |         1000 |

该复现不执行消息查询，仅获取 scope 就会线性累积回调，证明问题不依赖聊天历史体积或模型响应大小。实验结束后正常卸载上下文。临时分析工具和复现程序位于 `.tmp/heap-analysis/`，不提交解析出的字符串表或源码等快照派生数据。

## 修复方向与验证边界

1. 在数据库后端按稳定的所属生命周期标识复用 guard，而非按每次生成的 Context 包装对象复用。候选标识为所属 Fiber，但需要验证卸载、重新启用、依赖切换时的身份和代际语义；保留原有权限、插件命名空间和已卸载查询拒绝行为。
2. 覆盖同一 Fiber 经不同影子上下文高频调用、两个独立 Fiber、独立卸载、依赖切换及重新挂载。重复数千至数万次 scope/查询后，卸载回调数量应稳定；旧 scope 在所属生命周期结束后必须失效。
3. 再运行长期 IM 负载，比较 GC 后内存基线、回调数量及前后堆快照。当前只确认泄漏机制和本次快照中的大量持有对象，未计算精确支配树，也不宣称排除了其他次要泄漏。
4. 异常退出恢复另行处理。当前服务入口仅在退出码为 75 时自动重启；本次父进程退出码为 134，因此 watch 和 pnpm 仍存活到 06:49，并不表示业务服务仍运行。重启恢复可改善可用性，但不能修复内存积累。
